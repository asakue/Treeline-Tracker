# ADR-012: Миграция с Firebase на собственный бэкенд PostgreSQL 16 + PostGIS, REST API и WebSockets

* **Статус:** `ACCEPTED`
* **Дата:** Ноябрь 2026 г.
* **Авторы:** Даниил (ведущий архитектор), Кирилл (серверный разработчик), Александр (разработчик ядра)
* **Заменяет:** [ADR-003](./ADR-003-why-firebase-and-mock-repositories.md)

---

## 1. Контекст и Проблематика (Context)

На начальных этапах прототипирования Treeline Tracker использовал Google Firebase (Cloud Firestore, Firebase Authentication, Firebase App Hosting). В ходе полевых тестов и анализа требований поисково-спасательных служб (SAR) были выявлены фундаментальные архитектурные ограничения:

1. **Ограниченность пространственных запросов в NoSQL:** Cloud Firestore не имеет встроенного геопространственного движка. Реализация полигональных геозон безопасности и радиальных проверок требовала эмуляции через одномерные Geohash-диапазоны (`geofire-common`) и последующую дорогую фильтрацию на клиенте.
2. **Сетевые зависания SDK в оффлайне:** Несмотря на `persistentLocalCache`, Firestore Web SDK при обрывах связи пытается восстановить gRPC/HTTP-соединения, создавая скрытые задержки до 10 секунд и забивая сетевой стек.
3. **Требование суверенности и автономности (On-Premises / Edge Deployment):** В спасательных штабах МЧС и мобильных базовых станциях в тайге/высокогорье подключение к внешним облакам Google невозможно. Система обязана разворачиваться локально на полевом сервере/ноутбуке координатора через один `docker compose up`.
4. **Интеграция с радиомостами LoRa Mesh:** Необходимость прямого взаимодействия с брокером MQTT (Mosquitto) и аппаратными шлюзами без внешних вебхуков.

---

## 2. Принятое решение (Decision)

1. **Переход на PostgreSQL 16 с расширением PostGIS 3.4:**
   - Хранение геоданных в нативных типах `geography(Point, 4326)` и полигонах `geometry(Polygon, 4326)`.
   - Выполнение пространственных расчетов прямо в СУБД с аппаратным ускорением через индексы GiST (`ST_DWithin`, `ST_Contains`, `ST_Distance`).
2. **Собственный бэкенд на Node.js / Express + TypeScript:**
   - Использование современной легковесной ORM **Drizzle ORM** с типобезопасными схемами (`backend/src/db/schema.ts`).
   - Автономный REST API v1 (`/api/v1/auth`, `/api/v1/teams`, `/api/v1/tracks`, `/api/v1/waypoints`, `/api/v1/geofences`, `/api/v1/telemetry`, `/api/v1/emergency`, `/api/v1/mesh`).
   - Собственный WebSocket-сервер на базе библиотеки `ws` (`backend/src/websocket/`) с комнатами отрядов, heartbeat-контролем и выделенным каналом аварийного оповещения (SOS Rate-Limit Bypass).
3. **Автономная аутентификация и RBAC:**
   - JWT-токены с криптографической ротацией access- и refresh-токенов.
   - Хеширование паролей алгоритмами Argon2 / Crypto PBKDF2.
   - Строгие middleware-гарды (`AuthGuard`, `RoleGuard`).
4. **Контейнеризация и оркестрация:**
   - Подготовка единого `docker-compose.yml`, оркестрирующего PostGIS (`postgis/postgis:16-3.4-alpine`), MQTT-брокер (`eclipse-mosquitto:2.0`) и сервис бэкенда (`backend/Dockerfile`).
5. **Фронтенд-слой репозиториев (`src/infrastructure/repositories`):**
   - Реализация интерфейсов `IGroupRepository`, `IRouteRepository`, `IEmergencyRepository`, `ILocationRepository` через `BaseRestRepository`.
   - Автоматический прозрачный фоллбэк на локальное хранилище браузера (`LocalStorageRepository`) при отсутствии сети или в автономном режиме (`NEXT_PUBLIC_STORAGE_MODE=local`).

## 3. Последствия (Consequences)

### Положительные:
* **Мгновенные пространственные запросы:** Расчет нарушения геозон для сотен участников за миллисекунды прямо в PostGIS без пересылки избыточных координат.
* **Полная независимость от вендора:** Система на 100% открыта (Open Source), не требует платных облачных аккаунтов и может работать в изолированных локальных сетях (Air-gapped environments).
* **Единый стек TypeScript:** Общие типы, схемы Zod и валидаторы между клиентом, сервером и E2E-тестовым раннером.
* **Прямая интеграция с LoRa:** Бэкенд и MQTT-брокер обмениваются бинарными пакетами Meshtastic напрямую.

### Отрицательные / Риски:
* **Необходимость администрирования БД:** Ответственность за создание резервных копий (pg_dump) и мониторинг PostgreSQL ложится на оператора развертывания (компенсировано готовым `docker-compose.yml`).
